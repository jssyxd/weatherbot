**范围：** 仅 `tree6yes` 分支；未修改 `tree4`。  
**执行模式：** 始终为纸面/观察模式；代码不含钱包、私钥、签名、真实下单、撤单或改单路径。

## 2. 数据源与失败关闭约束

CheckWX 仍是当前观测的主源。AWC 只处理已发布 METAR/SPECI 的两个场景：首次/换日本地日暖机，以及 CheckWX 缺站或异常的灾备。AWC 响应会先归一化为 ICAO、原始报文和报告时间；现有的原始 METAR 温度解析、当地日筛选、报文新鲜度和温度精度检查仍会随后执行。

> AWC 不可达、返回空/异常数据、历史基线尚未完成、报告超过新鲜度限制、当日市场桶不可用或订单簿不可执行时，策略保持失败关闭。不会因预测、格点、再分析或仅凭盘口变化触发温度确认换手。

AWC 的官方 Data API 支持按照 `ids`、`format=json` 与 `hours` 查询 METAR，文档指出数据库最多保留 30 天、单次结果通常最多 400 条，且调用方应限制请求范围和频率。[1]

## 3. 五分钟受控观察模式测试

测试使用 49 个合同城市、`mode=observe`、`market_ws_enabled=false`、120 秒扫描间隔和临时状态目录运行 305 秒。为了不调用付费服务，测试环境刻意未设置 CheckWX 密钥，因此验证了“主源不可用时的 AWC 灾备”而**没有验证真实 CheckWX 凭据或套餐配额**。

| 项目 | 结果 |
| --- | --- |
| 运行结束 | 由预期的 305 秒测试超时停止，`timeout` 退出码为 124；进程正常写入“已停止”。 |
| 完成扫描 | 3 次；首轮在约 49 秒内完成，后续扫描对已知无合约状态不再重复刷新 Gamma。 |
| 扫描节奏 | 后两次完成扫描记录位于连续 120 秒边界。 |
| 当前数据灾备 | CheckWX 密钥缺失时，49 个站点均进入 AWC 两批近期查询；无真实订单动作。 |
| 暖机状态 | 按每周期 8 城的渐进策略运行；测试环境中 AWC 的间歇网络失败会标记为 `failed_awc_fetch`，尚未暖机城市显示为 `missing`，均不能生成策略信号。 |
| 市场规则 | Gamma 缓存处于 fresh；测试时远端大多数当前日期合约没有可交易规则，因此继续失败关闭。 |
| 实盘边界 | 临时目录未发现真实订单、签名、钱包或撤单调用痕迹。 |

测试过程中发现首次历史暖机和逐事件 Gamma 拉取可能因网络超时拉长首轮扫描。已采用分批暖机、受进程级超时限制的 AWC 调用、并发限时 Gamma 刷新及“明确失败同样缓存”的修复；最终测试成功完成三次扫描，后续扫描未被历史或市场发现卡住。

## 4. 部署说明

部署时使用 `config.example.json` 作为起点，在**运行进程环境**提供 `CHECKWX_API_KEY`，不要将密钥写入配置文件或提交到 Git。首次 49 城暖机是渐进的，默认每 2 分钟最多处理 8 城；在所有相关城市显示 `daily_warmup.status=complete` 前，受影响城市不会产生任何纸面入场、退出或换手信号。

实时盘口保护仍通过 `python3 metar_observer.py run` 启用；本次五分钟测试刻意关闭它，以隔离验证天气主源/灾备、暖机和市场结构刷新。生产纸面运行建议先观察健康快照中的 `untrusted_warmup_count`、`warmup_error_summary`、`last_current_source_summary` 和 `market_rules_fresh`，确认数据链路稳定后再评估策略研究结果。
